UPDATE HELPER
=============
A plain-English guide to how this app is built, so you can change or add
features yourself later without having to re-learn the whole codebase.


1. THE BIG PICTURE
-------------------
This is a desktop GUI app written in Python, using a library called
"customtkinter" (a modern-looking skin on top of Python's built-in tkinter
GUI toolkit). It downloads video/audio using "yt-dlp" (a very actively
maintained fork of youtube-dl), and optionally shells out to FFmpeg (for
merging/converting) and VLC (just to open files).

Three layers, kept deliberately separate:

  core/    -  no GUI code at all. Pure logic: talking to yt-dlp, reading and
              writing JSON files, checking for dependencies, moving files.
              You could reuse everything in here in a command-line tool.

  gui/     -  everything the user sees and clicks. Imports from core/ and
              calls it, but core/ never imports from gui/. This one-way
              relationship keeps things untangled - the logic doesn't know
              or care that a GUI exists.

  updates/ -  tiny standalone scripts, one per dependency, that just call
              functions already defined in core/dependencies.py. They exist
              so you (or a scheduled task, or a script) can update a single
              dependency from the command line without opening the app:
                  python updates\update_ytdlp.py

main.py is the entry point - it just calls gui/app.py's run() function. That
run() function (not main.py) is where startup wiring happens - installing
crash logging, then constructing the App and calling mainloop(). main.py
itself is deliberately kept to those three lines; if you need to add new
startup-time setup, it belongs in core/bootstrap.py's bootstrap() function
(called from run()), not in main.py.


2. HOW A DOWNLOAD ACTUALLY HAPPENS
-----------------------------------
gui/app.py's start_single_download():
  1. Reads the URL/name/type from the text boxes.
  2. Checks there's a default folder AND that FFmpeg is installed - if
     either is missing, it stops immediately and tells you why (this is
     the "tell the user what failed" behavior you asked for - previously
     the app would just silently do nothing).
  3. Spins up a new background thread (_run_single) so the window doesn't
     freeze while the file downloads.
  4. That thread creates a core/downloader.py Downloader object and calls
     .download_video() or .download_audio() on it.
  5. Downloader wraps yt_dlp.YoutubeDL(...).download([url]) with a
     "progress_hook" - a function yt-dlp calls repeatedly while it works,
     which we use to update the progress bar.
  6. Every exception is caught and wrapped in a DownloadStageError that
     records WHICH stage failed (info fetch / format selection /
     download-merge) so the error message you see is specific, not generic.
  7. When it's done (success, failure, or cancel), core/history.py logs an
     entry, and the UI re-enables the Download button.

Because everything after step 3 runs in a background thread, and tkinter
widgets can only safely be touched from the main thread, you'll see a lot
of "self.after(0, lambda: ...)" calls - that's how a background thread asks
the main thread to update a label/progress bar/etc safely. If you add new
background work, follow this same pattern: do the slow work in a thread,
and only touch widgets via self.after(0, ...).


3. THE TABS (gui/app.py)
-------------------------
The whole window is one CTkTabview with five tabs, each built by its own
_build_..._tab() method inside the App class. This is why there's no
separate pop-up window for Settings/History anymore - they're just frames
placed inside a tab instead of a Toplevel window, which is lighter on
memory and keeps everything in one place as you asked.

  _build_download_tab()   - the main workflow: single download + batch queue
                             (as an inner, nested CTkTabview), thumbnail
                             preview, progress bar, log box.
  _build_playlists_tab()  - a JSON file (playlists.json) mapping playlist
                             name -> list of file paths. "New Playlist"
                             opens a small dialog (gui/dialogs.py).
  _build_history_tab()    - reads/writes history.json via core/history.py.
  _build_settings_tab()   - reads/writes config.json via core/config.py.
                             Changing the default folder triggers
                             gui/dialogs.py's MoveFilesDialog, which lets
                             you pick (or Select All) which existing files
                             should move to the new location.
  _build_version_tab()    - calls core/dependencies.py's check_all() to
                             list every dependency's install status, with
                             per-item Install/Update buttons and one
                             "Update All" button.

To add a sixth tab: write a new _build_mytab(self, tab) method following
the same pattern, call self.tabview.add("My Tab") in _build_ui(), then
call self._build_mytab(that_new_tab_frame).


4. THE SCROLLABLE DROPDOWN
---------------------------
Stock CTkOptionMenu doesn't scroll - a 20-item list just becomes a giant
unscrollable menu. gui/scrollable_dropdown.py is a small custom widget:
a button that, when clicked, opens a borderless popup window containing a
CTkScrollableFrame full of option buttons. Any list-of-choices field in
this app (fonts, quality presets, aspect ratios) uses this instead of the
stock dropdown. To add a new dropdown field anywhere, do:

    my_var = ctk.StringVar(value="default")
    ScrollableDropdown(parent, ["A", "B", "C"], my_var, font=my_font).pack()

...and read the choice later with my_var.get().


5. DEPENDENCIES (core/dependencies.py)
----------------------------------------
Three different "kinds" of dependency, each checked and installed
differently:

  python  - customtkinter / yt-dlp / pillow. Checked with a plain
            `import module` inside a try/except. Installed with
            `pip install --upgrade <package>` run as a subprocess.

  ffmpeg  - has no installer; it's just two .exe files. We download the
            official static build zip from gyan.dev, unzip it, and copy
            ffmpeg.exe/ffprobe.exe into <app folder>\ffmpeg\bin. We then
            tell yt-dlp exactly where that folder is via the
            "ffmpeg_location" option - so nothing needs to touch the
            system PATH or need admin rights.

  vlc     - checked by looking for vlc.exe in the usual
            Program Files\VideoLAN\VLC location (or via `where vlc`).
            Installed by downloading VLC's real installer from
            get.videolan.org and running it with the silent-install
            switches /L=1033 /S. If Windows blocks the silent run (some
            locked-down PCs do), the code falls back to just opening the
            installer window for you to click through manually.

check_all() in that file returns a list every other part of the app reads
from - the dependency banner at the top of the window, and the whole
Version tab's list, are both just check_all() rendered as UI. If you add a
new dependency, add one dict describing it, teach check_all what to check,
and the Version tab / banner update automatically with zero other changes.


6. WHERE FILES LIVE (core/paths.py)
--------------------------------------
This matters a lot for a packaged .exe, in two separate ways.

First: when PyInstaller bundles everything into a single MediaDownloader.exe,
double-clicking it actually extracts the whole app into a hidden temporary
folder first (this is what sys._MEIPASS points to) - and that folder gets
deleted when you close the app. resource_path() finds bundled read-only
files (DISCLAIMER.txt, the settings gear icon, the updates/ scripts) inside
that temp folder when frozen, since those never change and ship with the app.

Second, and this one bit us in testing: writable data (config.json,
history.json, playlists.json, the downloaded ffmpeg/ folder) can NOT simply
live "next to the .exe" if the app is installed somewhere like
C:\Program Files\Media Downloader - that folder is protected, and a normal
(non-admin) Windows user gets a silent PermissionError trying to write
there. So app_dir() instead resolves to the standard per-user data folder,
%APPDATA%\Media Downloader (something like
C:\Users\<you>\AppData\Roaming\Media Downloader), when running as a frozen
.exe on Windows. When running from source (python main.py), it just uses
the project folder, which is simpler for development. Either way, whatever
app_dir() returns is where options/, history/, and ffmpeg/ get created.

If you ever add a new bundled read-only file, remember to also add it to
the --add-data line in build_exe.bat, or the .exe won't include it.


7. ADDING A NEW SETTING
-------------------------
Three places, every time:
  1. core/config.py -> add a key + default value to DEFAULT_CONFIG.
  2. gui/app.py's _build_settings_tab() -> add the widget that edits it.
  3. gui/app.py's _save_settings() -> add the line copying the widget's
     value into self.cfg[...], then save_config(self.cfg) writes it out.

Settings are read live from self.cfg wherever they're needed (e.g. the
Download tab reads self.cfg["video_quality"] at download time), so once
it's in config.json it's available everywhere.


8. COMMON THINGS YOU MIGHT WANT TO CHANGE
--------------------------------------------
"I want a different default video quality/format"
  -> core/downloader.py, edit VIDEO_QUALITY_MAP / VIDEO_FORMATS.

"I want to add a new audio format"
  -> core/downloader.py, add it to AUDIO_FORMATS - yt-dlp/FFmpeg support
     it automatically if FFmpeg's audio encoders support it.

"I want the window to open a different tab by default"
  -> gui/app.py _build_ui(), reorder the self.tabview.add(...) calls, or
     call self.tabview.set("Playlists") at the end of __init__.

"I want to ask for the download folder at startup again instead of at
 download time"
  -> gui/app.py: call self._prompt_for_download_root() near the end of
     __init__ (it used to be called there, as _ensure_download_root()).
     Currently it's only called lazily, from
     _ensure_download_root_for_download(), right before a download starts -
     so a first-time user can open the app and look around before ever
     being asked to pick a folder.

"I want to change the app icon"
  -> replace icon.ico in the project root (must stay named icon.ico, or
     update every reference to it in gui/app.py, build_exe.bat, and
     installer.iss).

"I want a totally new feature tab"
  -> see section 3 above.


9. RUNNING IT WHILE YOU EDIT
-------------------------------
You do NOT need to rebuild the .exe to test changes - just run:
    python main.py
directly from the project folder. Only rebuild with build_exe.bat once
you're happy and want a shareable .exe again.


10. WHY IT'S BUILT AS --onedir, NOT --onefile
------------------------------------------------
PyInstaller can package everything into either a single .exe file
(--onefile) or a folder containing the .exe plus its dependencies
(--onedir). --onefile looks tidier to share, but it works by silently
re-extracting the whole app into a temp folder every time it launches -
and that self-extracting behavior is exactly what a lot of antivirus/
Windows Defender heuristics flag and silently kill, with zero error
message and zero trace in any log, because the kill happens at the OS
level, entirely outside the Python program. That's a real failure mode we
hit while building this app. --onedir avoids the self-extraction step
entirely, starts faster, and is far less likely to get killed like that.
When sharing the app, zip up the whole dist\MediaDownloader\ folder (or
better, use the Inno Setup installer) rather than trying to hand someone
a single .exe file.


11. DIAGNOSTIC LOGGING (core/crash_log.py, core/startup_log.py)
--------------------------------------------------------------------
Three log files can appear in %APPDATA%\Media Downloader\ (or the project
folder, when running from source):

  crash_log.txt   - any normal Python exception, whether it happens during
                     startup (before the window even opens) or inside a
                     button click / background thread later. Comes with a
                     message box too, so a crash is never silent.
  startup_log.txt - a plain heartbeat, one line per startup stage,
                     flushed to disk immediately as each stage completes.
                     If the app dies with NO Python exception at all (a
                     hard native crash, or getting killed by something
                     external like antivirus), this is what tells you
                     exactly which stage it never got past - the last
                     line in the file is as far as it got.
  fault_log.txt   - Python's built-in faulthandler output, which can
                     sometimes catch true low-level crashes (segfault-style)
                     that bypass normal exception handling.

12. THE RECURRING-TASK SCHEDULER (_start_recurring)
--------------------------------------------------------
Two things need to run repeatedly for as long as the app is open: the
clipboard watcher (checks for a copied URL every second) and a heartbeat
(marks startup_log.txt every 3 seconds, forever). Both go through one
shared helper, self._start_recurring(interval_ms, func, label), instead of
each having its own hand-rolled self.after() loop with its own try/except.

Why this matters: a recurring self.after() loop is fragile by construction
- if the scheduled function raises and nothing reschedules it, the loop
just quietly stops forever with no error, which looks exactly like part
of the app "dying" even though the rest of the app is fine.
_start_recurring's tick() wrapper puts the reschedule call in a `finally`,
so the next tick is scheduled NO MATTER WHAT happened this tick - and any
exception is logged (both to crash_log.txt via core.crash_log.log_error,
and to startup_log.txt) rather than silently swallowed OR fatally killing
the loop. One bad tick is now just a log line, not a dead feature.

If you add a new recurring task, use this same helper:
    self._start_recurring(interval_ms=5000, func=self._my_task, label="my task")

The heartbeat specifically exists to answer "was the app actually alive
5 minutes in, or did it die 3 seconds after opening?" - previously
startup_log.txt only had a handful of fixed checkpoints in the first 2
seconds, so a crash any time after that left no trace of how long the app
survived. Now the last "heartbeat - event loop alive" line in the log IS
that answer, no matter how long the app ran before whatever happened.

Also added: self.protocol("WM_DELETE_WINDOW", self._on_close_requested)
- a normal user closing the window via the X button or Alt+F4 now logs
"WM_DELETE_WINDOW: user closed the window normally" before destroying the
window, so a future log can immediately tell the difference between "the
user closed it on purpose" and "it just stopped."


13. DPI AWARENESS TRACKING - TURNED OFF
--------------------------------------------
customtkinter runs a background poller (via its own internal .after() loop,
not a separate thread - it's safe with respect to Tcl's single-threaded
design) that checks roughly every 100ms whether the monitor's DPI/scaling
changed, so the UI can rescale itself if you drag the window to a monitor
with different scaling. This app doesn't need that - gui/app.py calls
ctk.deactivate_automatic_dpi_awareness() before the CTk root is even
created, which turns that whole poller off. This isn't a confirmed fix for
any specific bug, but it removes an entire always-running background loop
and its associated Windows ctypes calls from the picture, which is a
reasonable thing to trim regardless while chasing down anything
unexplained happening a few seconds into a session.


14. WINDOW SHOWS BUT ISN'T VISIBLE ON SCREEN (window centering / z-order)
------------------------------------------------------------------------------
A distinct failure mode from any of the above: the event loop runs fine
forever (heartbeats keep ticking in startup_log.txt), but no window ever
appears on screen. This isn't a crash at all, so none of the crash/fault
logging catches it - the window genuinely exists as far as Tk is
concerned, it's just not visible or reachable.

The likely cause: gui/app.py calls self.withdraw() immediately after the
CTk root is created, then later calls self.geometry("820x720") - a size
with NO explicit x/y position - while still withdrawn. On some Windows
setups, setting geometry on a withdrawn window and only supplying a size
(not a position) can result in the window reappearing at a stale or
off-screen position when deiconify() is finally called, rather than a
sensible default location.

The fix, in App.__init__:
  - _center_window(width, height) explicitly computes a centered x/y
    position from winfo_screenwidth()/winfo_screenheight() and sets
    geometry as "WxH+X+Y", instead of leaving placement to chance.
  - After deiconify(), the code also calls self.state("normal"),
    self.lift(), self.attributes("-topmost", True) followed by a delayed
    self.attributes("-topmost", False), and self.focus_force() - a
    belt-and-suspenders sequence to force the window to the front and
    grab OS focus, in case it was rendering successfully but simply
    landing behind other windows.
  - The taskbar icon (iconbitmap) is now set AFTER deiconify() rather
    than before - setting it on a still-withdrawn window is a separate
    known-flaky pattern on some Windows/Tcl-Tk combinations.

If a window-visibility bug like this ever comes back, startup_log.txt's
"deiconify() done - window state is now '...'" line is the one to check
first - self.state() should read "normal"; anything else ("withdrawn",
"iconic") means the window itself thinks it's still hidden.


15. THE WINDOW-SHOW SEQUENCE - SIMPLIFIED, withdraw() REMOVED
--------------------------------------------------------------------
App.__init__ used to call self.withdraw() immediately after creating the
window, planning to bring it back with self.deiconify() (plus lift(),
focus_force(), and a brief -topmost flash) once setup finished. That
withdraw() only ever existed to hide the window while a blocking
first-run dialog (the old default-folder prompt) ran during __init__.

That dialog doesn't exist anymore - the default-folder prompt moved to
being lazy, asked only when a download actually needs it (see section 8),
which happens later, in response to a button click, not during __init__.
So the withdraw()/deiconify()/lift()/focus_force()/topmost-flash sequence
was left behind solving a problem that no longer existed - and turned out
to likely be causing a new one: a window that visibly appears and then
disappears almost immediately is a known symptom of rapidly toggling
-topmost true/false on some Windows/GPU-driver combinations.

The fix: all of that is gone. App.__init__ now just builds the window
normally - title, centered geometry, icon, then all the widgets - and
never hides it in the first place. This is the standard, simplest pattern
for a Tkinter/customtkinter app, and it's what's used now.

If you ever have a genuine reason to hide the window during startup again
(e.g. a new blocking dialog before the UI is ready), don't reintroduce
manual lift()/focus_force()/topmost toggling to compensate - a plain
self.deiconify() is normally sufficient on its own to bring a withdrawn
window back correctly.


16. PATHS ARE ANCHORED TO main.py'S LOCATION, NOT THE WORKING DIRECTORY
-----------------------------------------------------------------------------
core/paths.py's app_dir() (and resource_path()) used to compute the
project root from core/paths.py's OWN file location - which happened to
equal main.py's folder, but only because of where paths.py sits relative
to it (two directories up). That's an implicit assumption, not a
guarantee, and it doesn't answer the more useful question directly:
"where did the user actually put this app?"

Now, _entry_script_dir() in core/paths.py answers that directly: it reads
sys.modules["__main__"].__file__ - Python always sets this to the actual
script that was run, i.e. main.py, resolved to an absolute path. Every
writable file (options/, history/, playlists.json, the downloaded
ffmpeg/) and every bundled resource (DISCLAIMER.txt, assets/, icon.ico)
is now explicitly anchored to that, not to os.getcwd() and not to an
assumption about folder depth. This was tested by literally running
main.py from a totally unrelated working directory
(python /path/to/app/main.py from inside /tmp/somewhere/else) and
confirming config.json still landed next to main.py, not in the random
cwd - so it doesn't matter how or from where the app gets launched.


17. PER-ENTRY HISTORY DELETION, ID MIGRATION
--------------------------------------------------
Every history entry now gets a unique "id" (a uuid4 string) when
add_entry() creates it, so a single entry can be targeted for deletion
without relying on its position in the list (which shifts every time a
new download is added, since newest entries go at the front).
core/history.py's delete_entry(entry_id) filters the stored list by id and
rewrites history.json. The History tab's row builder
(_refresh_history_tab in gui/app.py) now adds a "Delete" button per row,
wired to self._delete_history_entry(entry_id).

Backward compatibility: history.json files saved before this change won't
have an "id" field on their entries. load_history() checks for this on
every read and assigns a fresh uuid4 to any entry missing one, saving the
migrated file back immediately - so old history is still fully usable and
individually deletable, no manual migration step needed.


18. THUMBNAIL CLEARING
----------------------------
self._clear_thumbnail() resets both the CTkImage reference
(self.thumbnail_image = None - important so it isn't still held on to
after the label stops showing it) and the CTkLabel's displayed image.
_add_clear_button() takes an also_clear_thumbnail=True flag; the URL and
Name fields' own X buttons pass this so clearing either one also clears
whatever thumbnail was fetched for that download - the output folder
field's X button does not, since a thumbnail isn't tied to that field.


19. MANY MORE COLOR THEMES
------------------------------
customtkinter ships 4 built-in theme names: blue, green, dark-blue, and
gold. gui/app.py's COLOR_THEMES list now also includes purple, red, teal,
rose, slate, orange, cyan, and indigo - 12 total. Those 8 extra ones are
JSON theme files under assets/themes/, generated by taking
customtkinter's own blue.json as a template and replacing just its three
accent-color pairs (the main accent, its hover shade, and the dropdown-
menu hover shade) with a different hue's equivalents, leaving every
structural property (corner radii, border widths, neutral grays, font
settings) untouched. This guarantees every generated theme is fully
schema-correct across every widget type CTk uses, rather than risking a
hand-written theme file missing some CTkWidget's expected key and
breaking a particular screen at runtime.

apply_color_theme(theme_value) in gui/app.py is the one place that knows
how to load either kind: if theme_value is one of the 4 real customtkinter
names it's passed straight to ctk.set_default_color_theme(); otherwise
it's treated as one of ours and resolved to
resource_path(f"assets/themes/{theme_value}.json"). To add yet another
theme, drop a new <name>.json into assets/themes/ (or regenerate more via
the same template-substitution approach - see the generator logic used to
create the current 8, which is not itself a checked-in script but a short
one-off using Python's json module) and add its name to COLOR_THEMES.

Remember to keep build_exe.bat's --add-data "assets;assets" line as-is -
that already covers assets/themes/ too, so no separate packaging step is
needed for new theme files.


20. THE THUMBNAIL "image doesn't exist" CRASH - ROOT CAUSE + FIX
-----------------------------------------------------------------------
This one actually crashed in real use (confirmed from a submitted
crash_log.txt) and took real investigation to pin down, so it's worth
explaining properly.

Symptom: clicking a field's clear button, or fetching a second video's
info after the first one already showed a thumbnail, would sometimes
raise _tkinter.TclError: image "pyimageN" doesn't exist and take the
whole app down with it.

The first, smaller bug: _clear_thumbnail() and _add_clear_button()'s
do_clear() would call self.thumbnail_label.configure(image=None) even
when there was nothing to clear (no thumbnail currently shown), which
Tk doesn't handle gracefully. Fixed by checking
self.thumbnail_image is not None before ever touching the widget.

The second, deeper bug (the one that actually explains _show_thumbnail
crashing, not just clearing): even calling configure() with a BRAND NEW
CTkImage on the label - nothing to do with clearing at all - could still
raise the exact same TclError, referencing an OLD image's name. This was
tracked down with a direct reproduction: create image A, show it, clear
it, create a completely different image B, try to show it - B's own
configure() call would fail, even though B has never been shown before
and A was already gone.

The cause: once self.thumbnail_image is reassigned or set to None, the
OLD CTkImage's Python object has no more references anywhere and gets
garbage-collected. CTkImage apparently does some internal Tcl-level
cleanup when that happens, and CTkLabel's own internal bookkeeping about
"what image name is currently configured" doesn't get updated in sync -
so the NEXT configure() call, even with a totally unrelated new image,
can still reference the dead old name during its own internal update
logic and throw.

The fix (verified with a 10-15 iteration stress test that reliably
reproduced the bug before the fix, and passed cleanly after):
self._thumbnail_image_history (a plain list, set up in __init__) holds a
reference to every CTkImage this session has ever created, forever (or
technically capped at the most recent 30 - see the cap logic in
_show_thumbnail - to keep a very long session's memory bounded; 30 tiny
160x90 thumbnails is nothing). This means the underlying CTkImage objects
are simply never garbage-collected while the app is running, which
avoids whatever CTkLabel-vs-CTkImage desync causes the crash in the first
place. self.thumbnail_image (the single "what's currently shown" value)
still gets set to None on clear as before - that's a separate concern
from whether the object gets garbage-collected.

_show_thumbnail() also keeps a defensive try/except-and-retry-once around
the actual configure() call as a second line of defense, in case some
other, not-yet-understood variant of this same class of bug ever
resurfaces - if it does, it now logs a message instead of crashing the
app, which is a reasonable fallback for something as non-critical as a
thumbnail failing to display once.

If you ever see this exact TclError again somewhere else in the app
(e.g. if a new feature adds another place that swaps CTkImages on a
label), the fix is the same pattern: don't let old CTkImage objects get
garbage-collected while the app is still running.


21. THE REQUEST TRACKING SYSTEM (core/download_requests.py)
------------------------------------------------------------------
Every time a download is started with a URL present, one "request" gets
created and tracked - whether it's a single URL, a batch queue, or a
full playlist. This is separate from core/history.py (which is a flat
chronological log of individual file downloads): a request groups
everything that happened as part of ONE click of the Download button,
and is what powers retrying a single failed URL from a batch without
re-running the whole batch.

Two dicts, persisted together in one JSON file
(<app_dir>/history/download_requests.json):
  requests_in_progress - still running
  requests_completed   - every URL in the request has a final status
                          (success or failed) - MOVES here even if every
                          single URL failed, since the whole point of
                          this system is being able to look back at what
                          went wrong and retry it, not just record wins.

Request IDs look like "video_queue_download-5" - <type>-<n>, where type
is one of the 6 combinations of (Video/Audio) x (single/queue/playlist),
and n is a running count of how many requests of that exact type have
EVER existed (start_request() bumps a counter in the same JSON file;
deleting old history entries doesn't reuse numbers).

Retrying a single URL (see gui/request_history.py's _retry_url) doesn't
create a new request - it calls reopen_for_retry(), which moves the
WHOLE original request back to in_progress with just that one URL reset
to "pending", runs the download again, and then finish_request() re-
evaluates the whole request's overall status once it's done. This is
what makes a retried request's dot correctly flip from red/orange back
to green (or back to orange, if other items in that same request are
still failed) - the request's status is always recomputed from its
current items, never just patched in place.


22. RETRY-3-TIMES AND CANCEL CLEANUP (core/downloader.py)
------------------------------------------------------------------
download_with_retry() wraps a single download_video()/download_audio()
call, retrying up to MAX_DOWNLOAD_ATTEMPTS (3) times on any
DownloadStageError (network hiccups, transient extractor failures) but
NEVER retrying a DownloadCancelled - the user asking to stop should stop
immediately, not get retried behind their back.

cleanup_partial_files(out_dir, name) is called whenever a download is
cancelled mid-way. It only ever deletes files matching "{name}.*" in
that folder - since `name` is the exact, unique-per-item filename base
yt-dlp was told to use (see make_unique_name), this can never accidentally
touch a sibling item's already-completed file in the same batch/playlist
run, even though they're all sitting in the same folder. This was
specifically tested (see the test history in this conversation) with two
completed items and one cancelled item all in the same directory, to
confirm only the cancelled one's files get removed.


23. PLAYLIST AUTO-CREATION (gui/app.py's _run_playlist)
------------------------------------------------------------------
When "Download playlist" is on, the download flow takes a completely
different path (_run_playlist instead of _run_single): it first calls
core/downloader.py's fetch_playlist_info(), which looks up the
playlist's own title plus every entry's title/URL without downloading
anything. A new playlist is created via core/playlists.py's
create_playlist(), named after the playlist's own title - or, if the
site didn't report one, the first entry's title instead. Every entry
then downloads straight into that playlist's own folder
(self._playlist_folder()), and gets registered into the playlist via
add_to_playlist() as each one finishes successfully.


24. THE LOG'S BACKING LIST + COLOR CODING (gui/app.py's _log)
------------------------------------------------------------------
self._log_entries holds every log line ever written this session as
(level, message, color) tuples - level is "simple"/"detailed"/"developer",
color is None or one of "green"/"red"/"blue". The visible CTkTextbox is
just a filtered VIEW of this list at the currently-selected mode:
switching the Log Mode dropdown calls _on_log_mode_changed(), which wipes
the textbox and re-renders every entry whose level is at or below the
new mode - so switching to Detailed retroactively reveals detail-level
lines that were already logged while in Simple mode, rather than only
affecting future lines. clear_log() empties both the textbox AND this
backing list together - if it only cleared the textbox, switching modes
afterward would silently bring the "cleared" lines back.

Color tags (green="#2fa84f", red="#c0392b", blue="#3b8ed0") are applied
via CTkTextbox's own tag_config/insert-with-tag mechanism, lazily created
the first time each color is actually used. "Done: <path>" lines are
green, any error message is red, and a "Downloading..." line right
before each retry-wrapped download call is blue - wired directly into
_run_single/_run_batch/_run_playlist.

The "Developer" log mode option is gated behind the
dev_log_mode_enabled toggle in the Developer tab - it simply doesn't
appear in the mode dropdown's choices until a developer turns it on, same
as the Developer display mode for Request History (dev_request_mode_enabled).


25. DEVELOPER TAB IS DYNAMIC, NOT PERMANENT
------------------------------------------------------------------
Unlike the old version of this app (which had a permanently-visible "Dev"
tab with a password gate built into it), the Developer tab now genuinely
does not exist in the tabview until a correct login happens on the
Extras tab. _dev_login_clicked() checks credentials via
core/dev_access.py's check_dev_credentials() (which checks both the
built-in account and any accounts granted via the Grant Developer Access
section), and only on success calls self.tabview.add("Developer") for
the first time ever, or just switches back to it if it was already built
this session. Logging out calls self.tabview.delete("Developer") - the
tab is completely gone again, not just hidden/disabled.

core/dev_access.py stores any additionally-granted developer accounts in
their own file (<app_dir>/options/dev_access.json), password-hashed
(SHA-256, salted with a fixed app-specific string - a basic deterrent,
not a claim of serious cryptographic security for a hobby project's
local credentials file). Granting NEW access always requires the
PRIMARY built-in password specifically - a granted account can't itself
grant further access, which keeps the trust chain simple and bounded
rather than open-ended.


26. SMOOTH SCROLLING (gui/smooth_scroll.py)
------------------------------------------------------------------
Applied automatically to every CTkScrollableFrame anywhere in the app,
including ones added in the future - patch_smooth_scrolling() (called
once from core/bootstrap.py, before the App is constructed) wraps
CTkScrollableFrame.__init__ itself, so no individual call site needs to
do anything differently.

The actual mechanism: rather than touching customtkinter's mouse-wheel
event bindings directly (risky - re-implementing/overriding those means
either duplicating internal logic that might change between customtkinter
versions, or risking silently breaking scrolling entirely if a binding
assumption turns out wrong), it patches the underlying
canvas.yview_scroll() method that those bindings ultimately call. A
request to scroll by N units gets split into N individual 1-unit steps,
each fired ~8ms apart via .after() - the same total scroll distance,
delivered as a short animated glide instead of one instant jump. This
works regardless of what triggered the scroll (mouse wheel, scrollbar
drag, keyboard), since it intercepts at the mechanism level, not the
input level.


27. BACKGROUND COLOR + RESIZABLE LOG BOX (Settings tab)
------------------------------------------------------------------
Background color uses Python's own tkinter.colorchooser (stdlib, no new
dependency) - _choose_background_color() opens the OS-native color
picker, applies the chosen hex color immediately via
self.configure(fg_color=...) on the root window, and saves it to
cfg["background_color"] (None = use the current theme's own default,

on every future launch in App.__init__.

The log box height slider (cfg["log_box_height"], default 140px) applies

Download tab's other rows are fixed-size and only the log row has grid

space is available, which is what "resize the other contents based on
the size of the log" works out to in a standard grid layout - the log
grows/shrinks and everything above it stays put.


28. YOUTUBE BOT-DETECTION HANDLING
------------------------------------------------------------------
YouTube sometimes responds to rapid or repeated download requests with
"Sign in to confirm you're not a bot," refusing the download entirely.
This is handled as its own distinct case throughout the download
pipeline, not just another generic failure:

  core/downloader.py:
    - _is_bot_detection_error(exc) checks the exception text for this
      specific message (both straight and curly-apostrophe variants,
      since yt-dlp's own message uses a curly one).
    - YouTubeBotDetectedError is raised instead of the usual
      DownloadStageError when this is detected, in both
      download_video() and download_audio()'s exception handlers.
    - download_with_retry() explicitly never retries this exception
      (alongside DownloadCancelled) - retrying a bot challenge 3 times
      in a row accomplishes nothing but delay, since the block isn't a
      transient network hiccup.
    - _cookie_options(cookies_from_browser) builds yt-dlp's own
      "cookiesfrombrowser" option - this is yt-dlp's actual documented
      fix for this exact error: pulling cookies from an already signed-
      in browser session makes requests carry a real identity instead
      of looking anonymous/scripted. "none" (the default) changes
      nothing from before.

  gui/app.py:
    - _handle_bot_detection(request_id, url) is the one shared handler
      for all three download paths (_run_single, _run_batch,
      _run_playlist). It logs a red-colored explanation, marks that
      request item failed, and shows a yellow messagebox.showwarning()
      (not a plain error) with a plain-language explanation and 3
      concrete things that help: set Cookies from browser in Settings,
      wait before retrying, or increase the batch delay.
    - Critically, _run_batch and _run_playlist both `break` immediately
      after calling this - the WHOLE batch/queue/playlist stops right
      there, rather than continuing to the next URL and hitting the
      identical wall (and identical popup) over and over. That's the
      actual fix for "the log doesn't get flooded" - the flooding would
      come from repeating the same failure N more times, not from a
      single occurrence.
    - Settings tab has two new controls: a Cookies from browser dropdown
      (cfg["cookies_from_browser"], one of yt-dlp's own supported browser
      names) and a Delay between batch/playlist items slider
      (cfg["batch_delay_seconds"], 0-30s, default 3) - spacing requests
      out is the other real mitigation, reducing how often this gets
      triggered in the first place rather than just reacting to it after
      the fact. The delay itself is implemented as short (0.25s) sleep
      increments checked against the cancel flag each time, so a long
      delay doesn't make the Cancel button feel unresponsive.

If yt-dlp ever changes this error message's exact wording,
_BOT_DETECTION_SIGNATURES in core/downloader.py is the one place to
update - everything else keys off that check.


29. DUPLICATE DOWNLOAD DETECTION (Settings > Advanced)
------------------------------------------------------------------
core/download_requests.py's find_previous_download(url, out_dir) scans
every completed request for a prior SUCCESSFUL download of that exact
URL into that exact output folder, and confirms the file is still
actually there (a moved/deleted file no longer counts as a duplicate).
Wired into all three download paths in gui/app.py (_run_single,
_run_batch, _run_playlist) right after the output filename is decided -
a match logs a blue "Skipped - already downloaded to..." line, marks
the request item status "skipped" (a new status alongside pending/
downloading/success/failed - see finish_request()'s overall-status
calculation, which now treats all-success-or-skipped as an overall
"success"), and moves on to the next item without attempting the
download at all.

Retrying a single URL from Request History (gui/request_history.py's
_retry_url) never calls this check - it's a completely separate code
path that has no reference to find_previous_download anywhere in it, so
a retry always genuinely re-attempts the download regardless of this
setting, exactly as asked for ("pressing retry download buttons
completely bypass this").

cfg["duplicate_detection_enabled"] (default True) is the toggle, in
Settings > Advanced.

33. VERSION-SAFE SETTINGS EXPORT/IMPORT (core/config.py)
------------------------------------------------------------------
Export writes a small wrapper around the settings, not just the raw
config dict: {"_export_format_version": 1, "_exported_by_app_version":
"1.2", "settings": {...}} - export_config_dict() builds this.
_export_format_version is for THIS wrapper's own shape (bump it only if
the wrapper structure itself ever needs to change); the app version is
just informational, shown in the import report.

merge_imported_config(imported) is what actually makes this
version-safe in both directions, and it's built to need NONE of this
metadata to work - a bare flat settings dict (the old, pre-wrapper
format) or even a hand-edited JSON file with only two or three keys in
it imports correctly too:
  - Detects the wrapper (a "settings" key holding a dict) and unwraps
    it; if that's not there, treats the whole file as a flat settings
    dict directly - this is what makes an old export from before this
    wrapper existed still import cleanly.
  - Every key that's a KNOWN setting (exists in DEFAULT_CONFIG) and
    type-compatible with its default is applied. A settings file never
    needs to contain every key - anything missing is simply left at its
    current/default value, never an error.
  - A key that exists in DEFAULT_CONFIG but has an incompatible type in
    the imported file (e.g. a string where a bool is expected) is
    skipped, keeping the safe default, rather than risking the app
    breaking on a value shaped differently than it expects.
  - A key that ISN'T recognized by this version at all (e.g. a setting
    a NEWER version of the app added, being imported into an OLDER one)
    is preserved as-is in the merged config rather than silently
    dropped - so if the app is updated later and that setting becomes
    meaningful, it's still there.
  - Returns (merged_config, report) - report is a list of short,
    human-readable strings (how many settings were missing/filled from
    defaults, how many were unrecognized-but-preserved, which specific
    ones were type-mismatched and skipped) shown to the user via a
    popup after import, so a partial or cross-version import is never
    silent about what actually happened.

Only raises (ValueError) if the imported data isn't usable as a settings
source at all - not a JSON object/dict. Everything else - missing keys,
extra keys, wrong types, wrapped or unwrapped format - is handled
gracefully rather than treated as an error.

35. THE MEDIA TAB (Playlists renamed, plus a new Library subtab)
------------------------------------------------------------------
The tab that used to just be "Playlists" is now "Media", with an inner
CTkTabview holding two subtabs: "Playlists" (exactly what was there
before - gui/app.py's old _build_playlists_tab is now
_build_playlists_subtab, content untouched, just relocated) and the new
"Library" subtab.

core/media_library.py is the actual engine behind Library - built for
someone managing a lot of different KINDS of files, not just this app's
own video/audio downloads:
  - CATEGORY_EXTENSIONS covers Video/Audio/Image/Document/Archive/Code,
    with anything else falling into "Other" - categorize(filename)
    determines this from the extension alone (cheap, no file-content

  - _relevance_score(filename, query) is a deliberately simple ranking

36. ESTIMATED COMPLETION TIME (individual item + whole queue)
------------------------------------------------------------------
gui/app.py's _format_eta(seconds) turns a raw seconds count into a
short human string ("45s", "3m 12s", "1h 05m"), returning None for
anything nonsensical (negative, absurdly large from a speed spike) so
callers just show nothing rather than a misleading number.

Two independent things feed the combined ETA label (self.eta_label,
next to progress_label/queue_progress_label on the Download tab):
  - Per-item: self.downloader.last_eta_seconds, which core/downloader.py
    was already computing per-hook-call (remaining bytes / current
    speed, falling back to yt-dlp's own 'eta' field) - this was already
    there, just not surfaced in the UI before.
  - Whole queue: self._batch_item_durations (a list of completed items'
    real elapsed_seconds() from THIS run only - reset at the start of
    every _run_batch/_run_playlist call) and self._batch_items_remaining
    (decremented after every item, success/fail/skip alike). The
    estimate is average-completed-duration * items-still-to-start, plus
    whatever's left of the CURRENT item (its own last_eta_seconds, or
    the average if that's not available yet). Both get reset to empty/0
    in _set_downloading_state(False) once a run ends, and initialized in
    __init__ so single downloads (which never touch these) don't hit an
    AttributeError from _update_eta_label() checking them.

_update_eta_label() is called from _set_progress() (i.e. every progress
hook tick, same cadence as the percentage/speed display already
updates), building the combined string as "~Xs left | ~Ys for whole
queue" - the whole-queue half only appears when there's actually
tracking data to estimate from (single downloads and the very first
item of a run just show the per-item half).


37. CANCEL CLEANUP - RETRY WITH BACKOFF FOR LOCKED FILES
------------------------------------------------------------------
core/downloader.py's cleanup_partial_files(out_dir, name) used to try
deleting each matched partial file exactly once, silently giving up on
any OSError. The real problem: a cancel doesn't instantly release the
file - the DownloadCancelled exception has to unwind back up through
yt-dlp's own internals before it actually closes whatever handle it had
open, and on Windows specifically a file can't be deleted at all while
still open (unlike POSIX) - so a single immediate delete attempt right
after cancelling could genuinely fail with "file in use" even though
the file really was abandoned and safe to remove a moment later.

Now retries each file up to 6 times with a 0.2s delay between attempts
before giving up on it, and returns (removed, still_locked) instead of
just a flat list - callers (all 3 cancel-handling sites in gui/app.py)
now tell the user explicitly if something genuinely couldn't be cleaned
up (still locked by another process entirely, e.g. antivirus scanning
it) rather than that being silent. Verified with a mock that fails the
first 2 delete attempts before succeeding (retry actually recovers) and
a mock that never succeeds (correctly reported as still_locked, not
silently dropped).


38. MEDIA LIBRARY: DELETE BUTTON + DUPLICATE DETECTION
------------------------------------------------------------------
Delete button on every Library search result - a REAL, permanent delete
of the file at that path (not a "remove from view"), confirmed first
since there's no undo.

Duplicate detection is a new "Duplicates only" option in the Library's
existing Sort dropdown (core/media_library.py's SORT_MODES), not a
separate button - selecting it re-filters the current search results

_quick_fingerprint(path) is deliberately NOT a full-file hash - hashing

40. WEIGHTED MULTI-FIELD SEARCH + SPECIAL-CHARACTER-SKIP SORTING
------------------------------------------------------------------
core/utils.py's weighted_match_score(query, name, url, extra_fields)
and strip_leading_special(text) are the shared engine behind General
History's and Request History's search+sort - built once, used by
both, so they can't drift apart the way two separate implementations
eventually would.

weighted_match_score: a match in `name` ALWAYS outranks a match in
`url`, which ALWAYS outranks a match anywhere in `extra_fields` (a list
of secondary strings - status, error message, request id, file type,
per-item names, whatever's relevant) - via a tiered scoring scheme
(name: 200-240, url: 100-140, extra: 0-40) where even the weakest
possible name match outscores the strongest possible url/extra match.
Within a tier: exact match > starts-with > substring > partial word
overlap. Deliberately does NOT strip special characters - searching
".com" or ".org" needs those literal characters to actually match.
Returns 0 for "doesn't match anywhere."

strip_leading_special: the OPPOSITE behavior, used only for alphabetical
SORTING - drops leading non-alphanumeric characters so "[Cool] Video"
sorts under "C" rather than "[". Never applied to search text, only to
sort keys - kept as two clearly separate functions rather than one
flag-toggled function, so it's structurally impossible to accidentally
apply the sort-stripping behavior to a search query or vice versa.

Both gui/app.py's General History and gui/request_history.py's Request
History now: score+sort every entry/request by weighted_match_score
when a search is active (replacing the old "does the name contain
this substring" check), and use strip_leading_special() in every
alphabetical sort mode. "Oldest first" in General History was also
fixed to do a real chronological sort on the stored date rather than
reversed()-ing the current list order, which would have silently broken
once a search had already reordered that list by relevance.

Verified via direct unit tests (name-vs-url-vs-extra tier ordering, no
false positives, ".com"/".org" search still works) AND full GUI-level
tests confirming a name match actually renders before a url match in
both History subtabs' rendered widget text, plus the alphabetical sort
correctly ignoring a leading "[" bracket.


41. GENERAL HISTORY: LIVE PER-STAGE STATUS (Analyzing -> In Progress -> Success/Failed)
------------------------------------------------------------------
core/history.py's add_entry() now returns the new entry's id (instead of
the whole history list, which nothing was actually using), and there's
a new update_entry(entry_id, **fields) that mutates an existing entry
in place. This is what makes a single download show up in General
History the INSTANT it starts (as "Analyzing", using the URL itself as

Verified with a real download simulation that snapshots history state
mid-download (confirming it genuinely reads "In Progress" DURING the
call, not just after), confirms exactly one entry exists throughout
(no duplicate entries per stage), and confirms every status color
renders correctly by finding the actual subtitle label in the rendered
widget tree (not just checking the underlying data).


42. DRAFT TEXT-FIELD AUTOSAVE (1-hour freshness window)
------------------------------------------------------------------
core/draft_state.py is a small, separate JSON file (not part of
config.json - this is transient scratch state, not a real setting) that
saves the Download tab's in-progress text fields (URL, name, output
folder, batch queue contents, queue name) on every regular auto-save
tick, tagged with a timestamp. On the next launch, if that timestamp is
within 1 hour, the fields are restored and a log line confirms it; if
more than an hour has passed, load_draft_state() discards the file
itself and returns None - a stale URL/name typed over an hour ago is
more likely to be leftover clutter than something still wanted.
Nothing is saved at all if every field was empty (no point persisting
"nothing").

Verified with the full real cycle: type into fields on one App
instance, let a save tick fire, destroy it, construct a genuinely new
App instance (simulating a real relaunch) and confirm the fields come
back exactly as typed - plus confirmed an artificially-aged (2-hour-old)
draft is correctly rejected and leaves the fields empty, not restored.


43. COMPREHENSIVE SETTINGS EXPORT (history + request history bundled)
------------------------------------------------------------------
export_config_dict() now also bundles core/history.py's full history
list and core/download_requests.py's full requests data (both
in_progress and completed, plus the type_counters used for request-id
numbering) alongside the settings themselves - opt-out via
include_history=False if ever needed, but on by default since "make
updating more seamless" was the whole point.

Playlists and Media Library folders are NOT duplicated into the export
as data - they're real files/folders on disk, and copying media file
data through a JSON settings file isn't practical. Instead, the PATHS
to them (playlists_path, media_library_directories) are already part of
the regular settings, so pointing a fresh install at the same locations
picks them back up automatically without needing anything extra here.

merge_imported_config() now MERGES imported history/request data into
whatever's already on the current install, rather than overwriting it -
existing entries are matched by their own id (history entries) or
request_id (requests) and never duplicated or lost; only genuinely new
ones get added. This matters specifically because import could

77. WINDOW-RESIZE UNRENDER/RERENDER (settles only once the resize "drops")
------------------------------------------------------------------
App.__init__ binds <Configure> on the root window itself. This fires
continuously - many times a second - for the ENTIRE duration of a live
resize drag, not just once at the end, and also fires for window MOVES
(not just resizes) and for all sorts of unrelated child-widget geometry
changes that bubble up. _on_window_configure() filters all of that down
to just genuine root-window SIZE changes (event.widget is self, and the
new (width, height) actually differs from the last known size - a pure
move is correctly ignored).

On a genuine size change: a blank overlay (matching the window's own
background color) is raised over the entire window - "unrendering" in
the sense that it visually hides whatever's underneath while it's
still actively reflowing mid-drag, without anything underneath actually
being torn down or rebuilt. Every subsequent Configure event during the
same drag just resets a 200ms debounce timer rather than recreating the
overlay (a real, deliberate distinction - a naive non-debounced
implementation would flicker the overlay on and off constantly
throughout the drag, which is worse than not having one). Only once
that timer completes with NO further resize activity in between - the
window size has genuinely "dropped"/settled - does the overlay come
down, revealing the exact same GUI that was there the whole time.

Verified directly: no overlay at rest, one appears immediately on a
real size change, a simulated rapid burst of resize events (mimicking
a live drag) reuses the exact same overlay object with zero
flicker/recreation, the overlay correctly disappears once the
simulated drag stops and the debounce settles, and - importantly - a
PURE window move with no size change correctly does NOT trigger the
overlay at all, confirming the size-change filter genuinely works and
this isn't just reacting to every Configure event blindly. Also
confirmed normal field interaction (typing into url_entry) still works
correctly once a resize has settled.

80. FIXED: URL SCRAPER "EXECUTABLE NOT FOUND" - A REAL BUG IN MY OWN EARLIER FIX
------------------------------------------------------------------
Root cause found: core/url_scraper.py's ensure_playwright_browser_installed()
(built last round to fix installer-side browser downloading) called
`subprocess.run([sys.executable, "-m", "playwright", "install",
"chromium"], ...)`. This works fine running from source (sys.executable
is a real python.exe that understands -m). In the PACKAGED app,
sys.executable is the app's OWN compiled .exe - which does not
understand -m module-invocation syntax at all. It just receives
["-m", "playwright", "install", "chromium"] as plain arguments that
match none of this app's own recognized flags (--daemon,
--playwright-install), so it silently launched a redundant second copy
of the whole GUI app in the background and did nothing useful. The
browser was NEVER actually being downloaded for anyone using the real
packaged app - exactly explaining "the executable is not found" when
URL Scraping was attempted. My earlier testing never caught this
because it only tested from source, where this coincidentally works.

Fixed by calling Playwright's own public playwright.__main__.main()
entry point directly, IN-PROCESS (with sys.argv temporarily patched to
["playwright", "install", "chromium"]) instead of spawning ANY
subprocess for this. This sidesteps the whole problem architecturally -
it's a normal Python function call within the already-running
interpreter, so it works identically whether that interpreter is
frozen or not, since it never depends on sys.executable supporting -m
at all. Also found and removed an orphaned leftover return statement in
the same function (referencing an undefined variable, sitting
unreachable inside a finally block) from the same edit.

Verified this fix is real, not just plausible-sounding: ran the new
implementation successfully against this environment's actual
Playwright installation, THEN specifically simulated the frozen-app
failure condition by mocking sys.executable to a nonexistent path and
confirmed the install STILL succeeds - direct proof the new code
genuinely doesn't depend on sys.executable working correctly anymore,
unlike the old one (separately confirmed the OLD subprocess-based
approach does fail under that same simulated condition, for full
before/after contrast).

Second, related fix: gui/app.py's URL Scraper was dumping Playwright's
raw, technical "Executable doesn't exist..." error text directly at
the user via a generic error dialog, with no indication of what to
actually do about it. Now detects this specific error message and
offers to install the browser right there (reusing the now-fixed
ensure_playwright_browser_installed()) with automatic retry of the
original scrape once installation succeeds - any OTHER kind of scrape
error still shows the normal error dialog unchanged. Verified all three
paths directly: the missing-browser error correctly routes to the new
install-and-retry flow (not the raw error dialog), a genuinely
unrelated error still shows the normal dialog (confirming the
detection isn't over-broad), and a successful install correctly
triggers an automatic retry of the original scrape request.
